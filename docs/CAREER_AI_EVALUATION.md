# Career-stage AI evaluation

## Contract under test

- Each resolved PL/EN prompt records `career-v2.0.0:<stage>` in provenance. One shared evidence-safety base and exactly one stage module are included.
- Rubric: `technical-v1.3.0`. Category keys and numerical weights remain compatible. Labels and expectations differ by stage.
- One visible stage choice: `first_job`, `junior`, `mid`, `senior`, `lead`, `auto`. First job covers bootcamp graduates, university graduates and self-taught applicants. There is no separate context control.
- The selected stage is server-validated and persisted as the target. Historical `bootcamp` context values normalize to `first_job`; the internal context field is retained only for report/legacy compatibility. Analytics accepts the closed first-job stage enum without source content.
- No new account, panel, batch upload, pricing, payment or infrastructure changes.

## User promise

Early-career reports focus on fundamentals, concrete projects, personal contribution, technical decisions, testing, collaboration and CV clarity. Mid reports focus on independent delivery and decisions. Senior and Lead reports retain responsibility and scope assessment.

The Junior/Mid presentation has no seniority ladder. Category labels avoid organisational ownership and systems-thinking terminology for beginners. Level inference remains supporting model context, not the main diagnosis or a statement of real competence.

Personal, educational, team, open-source and internship work are admissible evidence. Bootcamp attendance does not imply either independence or dependence on a tutorial. The report distinguishes guided work from personal contribution only when the document supplies evidence.

No commercial experience, organisational scale, mentoring, revenue or customer counts are required for a good Junior CV. Strong evidence can receive a good score. A bootcamp context does not lower expectations for an explicitly selected Senior target.

## Scenario matrix

`fixtures/career-eval-cases.json` adds 11 paired PL/EN cases to the existing live runner:

| Cases | Expected behaviour |
|---|---|
| Strong first-job and bootcamp projects | Junior profile, score at least 80, no inappropriate senior advice |
| Junior with internship | Concrete execution and feedback; Junior profile |
| Mid | Independent delivery and decisions; Mid profile |
| Senior | Significant responsibility and contextual decisions; Senior profile |
| Technical Lead | Coordination and impact through others; Lead profile, no assumed people management |
| Guided-only bootcamp project | Junior or unclear, score at most 65; no invented independent contribution |
| Auto with strong bootcamp evidence | Infer Junior and use Junior scoring, not Senior expectations |
| Bootcamp applying for Senior | Perceived Junior, score at most 70 against Senior target |
| Career change | Transferable collaboration is valid; previous non-tech work is not developer employment |
| Junior job match | Educational projects meet explicitly permitted requirements; no commercial-experience penalty |

Thresholds are predeclared regression expectations for these specific synthetic inputs, not general scoring caps or guarantees about candidates.

## Required gates

- Schema, resolvable evidence, deterministic overall score, safe actions and PL/EN parity.
- No unsupported facts, metrics, commercial outcomes or invented independence.
- Appropriate stage-specific category language and presentation.
- No automatic score ceiling caused solely by first-job status.
- A weak certificate-and-stack-only CV must not get a strong score.
- Missing evidence is not missing competence. Do not manufacture findings to satisfy minimum counts.
- Equivalent PL/EN scores: overall difference at most 8; category difference at most 15; perceived level and simulated decision consistent.
- Inspect qualitative conclusions, suggested rewrites and prioritisation manually in both languages.

## Local checks and limits

`tests/career-quality.test.ts` checks example schema/evidence/parity and detects deliberately corrupted scores, classification and inappropriate advice. `tests/career-review-pipeline.test.ts` verifies the model request and server reweighting with a fake provider. API and browser tests cover context selection, clean handoff links, persistence, and the unpaid boundary.

Examples are curated synthetic reports, not outputs claimed to have been generated by a live model. Pattern checks are regression tripwires; they cannot prove semantic correctness or natural language quality.

The live runner now includes these cases, passes context to the model, and applies the expectations to actual returned reports. A targeted live Preview run and manual review of four generated PDF cases completed on 2026-10-09; see `CAREER_PREVIEW_QA_2026-10-09.md`. The entire eleven-case PL/EN matrix has not been executed. Do not treat local tests as proof that a live model meets this quality bar.

## Single-call routing and examples

`src/lib/ai/prompts/stages/` has separate First job, Junior, Mid, Senior, Lead and Auto modules, each in PL/EN. `getReviewPrompt` selects one module based on the validated target before the provider request. Generic canary expectation tables are removed from the shared base, so they do not duplicate the selected stage instructions. Auto performs inference and assessment within its single prompt; it does not run one model per stage. Retry/fallback requests may still occur on eligible provider errors.

Paired source cases mentioning bootcamp are retained as different educational backgrounds under the same first-job stage. They are quality fixtures, not separate product contexts. Public example pages have a fixed target for the selected example URL and no stage picker; the upload form links to the corresponding example before analysis.

The local pipeline test verifies exactly one request per locale for the first-job target. All six prompt routes are checked in both locales. The subsequent release ran four targeted live Preview analyses; broader coverage remains a separate gate.

Persistence requires `supabase/migrations/20261009194033_first_job_stage.sql` before deploying this code. It extends the target constraint and purchase-measurement allowlist; payment validation and service-role privileges remain unchanged. This migration has not been applied to any remote environment.

The migration was executed against an isolated in-memory PostgreSQL instance. Checks passed for legacy-row retention, first-job insertion, invalid-stage rejection, unchanged payment mismatch handling, idempotent fulfillment, first-job purchase measurement and service-role-only function execution.
